## The two arms, precisely (read this session, riir-infer `develop` @ 4c04911-era)

### Arm A — the incumbent `recurrence_f32_fused_rows_hd128` (deltanet.rs:1195-1280)
- Grid `(n_head, 128)`, block `(32,1,1)`, 0 smem — **one warp per (head, state-row)**; every warp holds the FULL 128-wide row as `s_c[4]` at column `c*32+lane`.
- Per token t: (1) READ pass — `sd = s_c[c] * decay; s_c[c] = sd; partial += sd * k_c[c]`; (2) kv_mem = **xor butterfly 16/8/4/2/1** (5 shuffles); (3) `delta_row = beta * (v_row - kv_mem)`; (4) WRITE pass — `s_new = s_c[c] + k_c[c] * delta_row; partial2 += s_new * q_c[c]`; (5) out = **xor butterfly 16/8/4/2/1** × scale. **10 shuffles/token/(head,row) warp.**
- State touched once per chunk (register-carried across p, line 2046-2049 doc: "bit-identical to p sequential launches").

### Arm B — the Yukon L8 reference (`gated_delta_net_kernel.cuh` @ 36c9536; Research 284 quotes verified 10-18)
- `gdn_cols_per_warp = 4` on Ampere+/S_v==128; the L8 lane→row PERMUTATION puts **8 lanes per column-group** (2 rows/warp), so the first two butterfly steps become the explicit register fold `__fadd_rn(__fadd_rn(p[0], p[2]), __fadd_rn(p[1], p[3]))` (kernel.cuh:530) and the remaining 3 steps run at width 8 — **40 → 6 shuffles/token** (source-stated), plus `gdn_precompute_raw_gates` (host-side gate precompute, kernel.cuh:510) and the `GDN_L8_MIN_TOKENS 17` prefill-class ubatch gate (:498-505).
- THEIR bit-identity anchor is their OWN xor 16/8/4/2/1 tree (the lazy-rollback per-warp checksum reads the stored base in the OLD layout order — that's why they preserved it). OUR anchor is DIFFERENT: our rowpar's fold order is the xor butterfly itself. **The port's central question is therefore the FOLD-TREE EQUALITY oracle**: does the L8 permuted order compute OUR kv_mem/partial2 sums in OUR order?

## The fold-tree oracle (G1 gate design — CPU-testable BEFORE any port)

Research 284 names it: "CPU-testable oracle (fold-tree equality)". Concretely, in `riir-infer/src/deltanet/` (the CPU substrate, no GPU needed to AUTHOR or RUN):

1. Model both orders over a 32-lane × 4-col partition with symbolic leaves: our order = xor butterfly on 32 lanes (pairwise lane-exchange, offsets 16→1); the L8 order = register pairs (p[0]+p[2], p[1]+p[3]) then xor at offsets 4/2/1 within the 8-lane group (VERIFY the exact offsets against kernel.cuh at the pin — Research 284 says "the rest run inside the 8-lane group", the offsets must be read, not assumed).
2. Bit-equality holds iff the two reduction TREES are the same binary tree over the same leaf multiset with the same left/right child order at every node. Floating-point addition is non-associative → the TREE, not the grouping width, is the invariant.
3. Expected outcome (to verify, not assume): with the L8 lane→row permutation chosen so lane l holds columns {l//8, 4+l//8} pairs (their map), the register fold (p0+p2)+(p1+p3) over 4 sub-partials IS a different tree than xor-16-first over the same 32 leaves → **likely NOT bit-identical to rowpar**; the arm then re-classes from "bit-identical by construction" to "reduction-order-pinned local kernel" — which per the Issue-940 determinism law is ADMISSIBLE if and only if the fold order is pinned in code and the result never crosses the sync/quorum boundary raw (prefill logits feed sampling, local-only → admissible with the pin). The plan proceeds EITHER WAY; what changes is the promotion gate class (G1 bytewise vs G1-reclassified-order-pinned at the site, decision recorded per the law).
4. If (3) resolves NOT-identical: re-derive the L8 permutation so the tree IS ours (a permutation of leaf ASSIGNMENT never changes a butterfly tree — xor exchanges are symmetric — so the register-fold shortcut is the ONLY divergence source; a variant keeping the full 5-step butterfly but gaining the 2-rows/warp load geometry would be strictly bit-identical and still kills the memory-side redundancy. Price BOTH variants in the bench.)
